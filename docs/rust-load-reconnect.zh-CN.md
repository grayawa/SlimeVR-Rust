# CPU 满载后的追踪错乱：重连校准修复

日期：2026-10-07。现象是设备仍在线，VRChat 点位错乱，并再次提示完整重置。

已确认 Rust 接收端的一处错误：同一 MAC 再次发送 UDP 握手，会递增接收会话；算法把会话变化当作 IMU 重新启动，清空完整重置和安装方向重置的修正四元数。主机处理停顿、漏发保活后，设备可能重新握手，而 IMU 本身并没有重启。原版 Java 的 `TrackersUDPServer.setUpNewConnection` 会复用设备和 Tracker，保留旋转修正；状态变化还可能单独设置 `needReset`。

## 本次处理

- 已知 UDP 设备重新握手时保留校准修正，包括完整重置、安装方向和 yaw 修正。首次连接仍从未校准状态开始。
- 接收会话仍然递增；拒绝旧会话样本，丢弃旧姿态、位置、速度、接触历史和滤波历史，等待新会话数据。
- 第一条新旋转直接初始化滤波器，避免从占位单位四元数预测或平滑产生错误旋转。
- HID、SteamVR、OSC 等来源的会话重建行为保持原来的语义。旧事件录制没有 `preserve_calibration` 字段时默认不保留校准。
- 后端 tick 间隔超过 100 ms 时产生 `warn` 级别 `runtime_stall`，记录 `at_ms`、`tick_gap_ms` 和 `expected_tick_ms`。连续停顿最多每 10 秒记录一次，默认日志级别可以看到。

UDP 握手没有可靠的 IMU 启动标识，不能仅凭重新握手判断传感器坐标参考是否重启。设备确实重启、佩戴位置变化或旋转参考变化后，仍需手动重置。

## 已验证的范围

回归覆盖接收端到算法端的 MAC 不变、端口变化、完整及安装方向校准保留、旧会话拒绝、新姿态恢复、预测和平滑滤波的首条样本，以及旧事件兼容。

真实 UDP / SolarXR WebSocket / SteamVR Unix IPC 模拟联调使用六台虚拟追踪器与头显输入。完成完整重置和安装方向重置后暂停后端 3.3 秒；模拟设备以 2 秒无保活作为重新握手条件，该数值是测试设置，不代表所有真实固件的超时值。

| 场景 | 旧后端 | 修正后端 |
| --- | --- | --- |
| 仅头显数据中断 0.8 秒 | 世界锚点暂时失效，六台校准仍保留 | 相同 |
| 后端停顿触发六台设备重新握手 | 六台完整和安装方向校准全部丢失，位置错乱 | 六台校准保留，位置恢复 |
| 检查 IPC 输出 | 左脚位置由约 `(-0.13, 0.12, 0.10)` 变为 `(0.13, 0.46, 1.04)` 米 | 恢复为约 `(-0.13, 0.12, 0.10)` 米，六个输出状态正常 |

另做了 8 个工作进程竞争同一个逻辑 CPU、后端设为低调度优先级的测试。旧后端的那次运行没有触发重新握手；修正后端的一次运行记录到约 1.4 秒 tick 间隔，六台设备都重新握手，负载结束后校准和位置保留。两次运行的主机其他负载不同，不能作为严格的性能 A/B，也不能据此宣称已复现 Windows / VRChat 的完整实机问题。暂停测试验证的是调度停顿后的错误恢复路径。

## 实机核对

使用修正版，完成正常校准后重复之前的操作。若再次错乱，记下发生时间及停止 CPU 密集任务后是否自行恢复，保留 `%APPDATA%\dev.slimevr.SlimeVR\logs` 内日志。先用默认 `info` 日志即可；需要姿态快照时再退出程序并以调试脚本重启。

核对同一时间附近是否有 `runtime_stall`，以及同一 `device_key` 的 `device_connected` 是否会话递增并带 `preserve_calibration: true`。没有这些事件时，还需调查 SteamVR 输入、驱动调度或其他路径。本修复不能保证主机长期得不到 CPU 时间时仍维持实时追踪。
